## D-001 — Expo for web + mobile (planning)
Context: one codebase for web, Android, iOS. Owner knows React Native.
Options: Expo / bare React Native + separate web / Flutter.
Decision: Expo with Expo Router and react-native-web.
Consequences: web and native share screens; platform-specific code goes in `.web.ts` /
`.native.ts` files.

## D-002 — Images on device, videos on server (planning)
Context: images are small and the math is cheap; on-device FFmpeg for React Native is no
longer maintained.
Decision: Skia + TypeScript core for images; FastAPI + FFmpeg + NumPy for videos.
Consequences: no per-image server cost; privacy promise for photos; server needed only for
video.

Context: owner wants ₹0 until launch. Hugging Face Docker Spaces now need a paid plan.

DuckDNS) for video; own PC + Cloudflare Tunnel as testing backup.
Consequences: ₹0 now; must stay within 2 OCPU / 12 GB; server kept portable so moving to
Hetzner is quick.

## D-006 — Skia spike setup + web encode finding (2026-10-01)
Context: task 0.2 — prove Skia can decode → read RGBA → write → encode on web and Android.
Decision: `@shopify/react-native-skia` 2.6.2 and `expo-image-picker` ~57.0.20 (both via
`npx expo install`; both ship inside Expo Go for SDK 57, so no dev build is needed yet).
Web loads CanvasKit lazily with `<WithSkiaWeb>` only on screens that need Skia
(`*.web.tsx` wrapper; skipped during static rendering), not via a custom entry file, so the
rest of the site does not wait for the 8 MB wasm. `public/canvaskit.wasm` is copied by a
`postinstall` script (`setup-skia-web public`) and gitignored.
Pixels are always read as `RGBA_8888` + `AlphaType.Unpremul` so the core math sees the same
bytes on every platform.
Finding (CanvasKit benchmark in Node, 2528 × 1696): decode ~100 ms, readPixels ~5 ms,
PNG encode ~1.5–1.8 s, JPEG q95 encode ~0.14 s, WEBP ~1.5 s. So on web, PNG encoding alone
misses the 1.5 s target.
Consequences: Phase 2 on web should encode PNG output with the browser's own encoder
(canvas `toBlob`) or keep JPEG inputs as JPEG; native Skia encode is expected to be fast
(Android timing still to be measured by the owner on a device).

## D-008 — Mask source, format and templates (2026-10-01)
Context: task 1.1 needs alpha masks; no black-background fixtures yet.
Options: calibrate from our own black Gemini images / port masks from an MIT project.
Decision: port the calibrated PNG masks from GargantuaX/gemini-watermark-remover (MIT,
masks by AllenK, MIT; license checked and credited in THIRD_PARTY_NOTICES.md). PNG sources
live in `src/core/masks/source/`; `scripts/build-masks.cjs` (uses `canvaskit-wasm`, already
installed with Skia, no new dependency) turns them into `src/core/masks/alpha-*.json`
(`alpha = max(r,g,b)/255`, one byte per pixel, base64) so core loads them with no image
decoder, in Node, on device and from a remote URL later. The 36 px mask is an area-average
downscale of the 96 px mask (not calibrated — verify with fixtures).
Templates in `masks.json` (logo size / right+bottom margin): 48/32, 96/64, 48/96, 36/96,
96/192 (May 2026 mask). Sources: 48/32 and 96/64 from the upstream README and
`watermarkConfig.js`; 48/96, 36/96 and 96/192 (with `alphaVariant: 20260520`) from upstream
`src/core/geminiSizeCatalog.js` at commit 07b059a. 48/96, 36/96 and 96/192 are UNVERIFIED
until our own fixtures confirm them (task 1.4); drop any template the fixtures do not
support. Threshold starts at 0.35, search radius ±8 px.
`scripts/build-masks.cjs` needs `canvaskit-wasm`, pinned as devDependency 0.41.0 (same
version Skia 2.6.2 uses, deduped).
Core tests run in Jest's `node` environment (`@jest-environment node` docblock), and an
ESLint `no-restricted-imports` rule blocks React / React Native / Expo / Skia / app imports
in `src/core`, and `no-restricted-globals` blocks window/document/navigator/atob/btoa/Buffer/process.
Consequences: when Google changes the logo, either re-run calibration from black images or
add a new mask JSON + template; no app code change needed.

## D-009 — clean(): verify after removal (2026-10-01)
Context: review of 1.3 showed a wrong template can score above the 0.35 threshold
(e.g. a 96 px logo scores 0.41 on the 48/96 template). Removing with the wrong mask damages
the corner.
Decision: `clean(img)` = detect → remove → verify, and returns the ORIGINAL image with
`detected: false` if (a) the box is not smoother after removal (variance of max(r,g,b)
did not drop — docs/04-algorithm.md step 4) or (b) any template still matches the cleaned
box with NCC ≥ 0.2 (`RESIDUAL_MAX_SCORE`; synthetic tests: right mask ≤ 0.06, wrong ≥ 0.26).
Costs one extra detect (~18 ms on 2528 × 1696).
Known limitation: an unknown new logo that CONTAINS a smaller known logo (e.g. a 48 px logo
when only the 36 px mask is known) still gets "cleaned" with the small mask. Captured as an
`it.failing` test in `clean-test.ts`. Mitigation: ship the new mask (remote masks, Phase 5).
Consequences: Phase 2 calls `clean()`, not detect/remove directly.

## D-012 — Image decode/encode: Skia on device, browser canvas on web (2026-10-02)
Context: task 2.3. D-006 measured CanvasKit PNG encode at ~1.6 s for 2528 × 1696 on web.
Options: CanvasKit on web too (same code path, slow PNG, 8 MB wasm) / browser canvas on web.
Decision: `features/image/image-io.ts` (Android/iOS) uses Skia: decode → RGBA_8888 Unpremul →
core → `encodeToBytes` → file in the app cache (`expo-file-system` ~57.0.7 added as a direct
dependency, `new File(Paths.cache, …).write()`). `image-io.web.ts` uses
`createImageBitmap(blob, { colorSpaceConversion: 'none', premultiplyAlpha: 'none' })` +
`getImageData` to decode and `canvas.toBlob` (PNG, or JPEG 0.95) to encode, returning an
object URL. The CanvasKit wasm is no longer needed by the product on web (only by the dev
spike and the Node fixture test). Output: PNG stays PNG; JPEG/WebP → JPEG 95; name
`<original>-clean.<ext>`.
Consequences: web and native use different codecs, so tiny encoder differences are possible;
`src/core` is shared and unchanged. Object URLs must be revoked when results are dropped.

## D-013 — Real fixtures: refine step, verification, 1.4 metric (2026-10-02)
Context: first real fixtures (3 × 2K Gemini PNG, 2752×1536, 1536×2752, 2048×2048).
Findings:
- All three carry the May-2026 96 px logo at margin 192 (`g96-m192`), at exactly the expected
  position. NCC scores 0.49, 0.50, 0.91.
- Detection on textured photos can land 1 px off (1536×2752 → y 2463 instead of 2464), which
  leaves thin dark/light lines on the logo outline. Added `core/refine.ts`: try ±2 px and keep
  the offset whose result has the least edge energy over a fixed area; it picks the exact
  position on all three.
- Logo-free crops of real photos scored up to 0.53 on some template (above the 0.35
  threshold!), so the score alone cannot decide. The variance check (box must get smoother)
  separated them perfectly: real logos 0.35–0.87 of the original variance, logo-free crops
  1.11–7.9.
- The D-009 residual re-detect check is REMOVED: photo texture in the cleaned box matched a
  template at up to 0.55 and it rejected all three real images. `clean()` is now
  detect → refine → remove → variance check.
- Task 1.4 metric: "mean excess brightness < 3" assumes a plain background and fails on
  textured photos that are visibly clean. Replaced with the outline edge ratio (mean
  brightness step on the logo outline ÷ elsewhere in the box): 2.5–6.3 before, 0.83–1.08
  after; must be < 1.3. Before/after crops were checked by eye and are clean.
- Fixtures were in `apps/app/assets/`; moved to `fixtures/` (names in `fixtures/SOURCES.md`).
- `@types/node` 24.19.0 added as a devDependency for `__tests__/fixtures-test.ts`
  (canvaskit decode in Node; jest-expo's TextDecoder lacks utf-16le, so the test swaps in
  Node's).
Consequences: threshold stays 0.35. Still unverified on real files: the 48/32, 96/64, 48/96
and 36/96 templates, JPEG-saved images, and non-Gemini photos (none supplied yet).

## D-014 — Keep provenance metadata (C2PA) in cleaned images (2026-10-02)
Context: review found every real Gemini PNG carries a C2PA Content Credentials manifest in a
`caBX` chunk (23–31 KB) and our re-encode dropped it — against CLAUDE.md rule 6 (do not strip
provenance metadata).
Decision: `features/image/provenance.ts` (pure, tested) copies the original's provenance
blocks byte for byte into the encoded output: PNG `caBX` chunks right after IHDR; JPEG APP11
(JUMBF) segments after SOI/APP0/APP1. `clean-image.ts` now reads the original bytes first
(native `File.bytes()`, web `fetch(blob)`), decodes from them, and stores the output under
its final name (native: own cache folder, so the gallery shows `<name>-clean.png`).
Verified: fixture test (all 3 keep a byte-identical `caBX`) and the web e2e run.
Consequences / for the owner: the manifest is kept but its hash no longer matches the edited
pixels, so C2PA validators will report the image as modified — the honest outcome. Not
covered: WebP inputs (converted to JPEG; WebP's C2PA lives in a RIFF chunk, not carried) —
`CleanedImage.provenanceKept` reports this; follow-up before release. Also still to check on
Android: that expo-image-picker (`quality: 1`, no editing) hands us the original bytes.

## D-015 — Outline-edge verification replaces "score + variance" (2026-10-02)
Context: a regression test on 60 random logo-free crops of the real fixtures showed 9 false
positives with D-013's logic: texture reached NCC 0.38–0.65 AND removal lowered the box
variance — `clean()` would have damaged those photos.
Decision: `core/verify.ts` `outlineEdgeRatio` (mean brightness step on the mask outline ÷
elsewhere in the box, +1 in the denominator for flat areas). Real logos 2.43–5.68, all 60
logo-free crops ≤ 1.47. `clean()` = detect → refine → require ratio ≥ `minOutlineEdge` (2.0)
→ remove → require ratio ≤ `maxOutlineEdgeAfter` (1.5; real 0.77–0.99, wrong removals
1.65–11) → require lower variance. Both limits live in `masks.json` (remote-tunable).
The D-009 "superset" limitation (48 px logo cleaned with the 36 px mask) is now caught; its
`it.failing` test is a normal test.
Consequences: on very grainy photos the soft May-2026 logo can fall under 2.0 (synthetic
noise ±12/pixel: 1.84), so the logo may be left in place — the safe failure (image unchanged,
"No Gemini watermark found" message). Thresholds rest on 3 real images; re-check when more
fixtures arrive. Supersedes the verification parts of D-009 and D-013.

`provenanceKept` flag of D-014). Share failures and partial batch saves have their own copy.

in the owner test and move it to a worklet runtime if taps feel stuck (> ~200 ms).

## D-017 — Video server: Veo mask, pipeline, provenance, limits (2026-10-02)
Context: tasks 3.1–3.3 with the owner's two 720p Veo fixtures.
Decision:
- Veo logo = same sparkle as images, 48 px at margin 96 on 720p (also listed upstream:
  48/72 on 720p, 72/108 and 72/144 on 1080p), at **0.62 × the image opacity** (fitted: scale
  1.0, no sub-pixel shift; outline after 1.2 → ~1.0 with cleanup). Masks `alpha-veo-48`,
  `alpha-veo-72` (derived, 1080p unverified) in `masks.json` → `videoTemplates`; the app ignores
  them. No upstream code copied (catalog geometry only, MIT, already credited).
- Server = NumPy port of `src/core` (`server/app/detect.py`): candidates per template, best
  score first, the first that passes D-015 verification wins (texture made a 1080p template
  outscore the real one on veo-2). The same change went into the app core (`candidates()`).
- Detection on the mean of the first 30 frames, then per frame: reverse blend + 3×3 median on
  the logo outline band (docs/04 "edge cleanup"; H.264/4:2:0 leaves a faint ring otherwise).
- ffmpeg rawvideo rgb24 pipes with explicit BT.709 both ways; libx264 CRF 18 veryfast,
  yuv420p, same fps (exact rational), audio stream-copied, `+faststart`.
- Provenance: Veo MP4s carry a C2PA manifest in a top-level `uuid` box
  (d8fec3d6-1b0e-483c-9297-5828877ec481). It is appended to the end of the output file so no
  chunk offsets move; its hash no longer matches (honest "modified").
- Limits: 100 MB (streamed check), 60 s, 1080p → new code `422 too_big_resolution`;
  10 videos/IP/hour in memory → new code `429 rate_limited`; CORS = Expo web on :8081
  (`SAAF_CORS_ORIGINS`); job folder deleted after the response or on any error, plus a 15-min
  sweeper thread. Heavy work runs in a thread pool, max 2 videos at once.
- New dependencies: numpy 2.5.3, python-multipart 0.0.32.
Results: veo-1 (10 s) cleaned in 2.6 s, veo-2 (8 s) in 2.1 s on the dev PC; frames, fps,
duration and audio unchanged; logo not visible in output frames.
Consequences: contract and DESIGN copy gained two codes. Rate limit and job slots are per
process (fine for one server; Redis only if we scale out).
Addendum (2026-10-02, 3.4): default CORS allows any localhost port (regex) because Expo web
moves to the next free port when :8081 is busy (it was, on the owner's PC). Setting
`SAAF_CORS_ORIGINS` switches to an exact list (production). `apps/app/.env.example` documents
`EXPO_PUBLIC_API_URL` for web / emulator / phone; `apps/app/.gitignore` now ignores `.env`
(the app has its own git repo, so the root .gitignore does not apply there). About shows a
dev-only server status line. Verified: Expo web dev build on :8083 → "connected (v0.1.0)".

## D-018 — Video flow in the app: upload, link mode, preview (2026-10-02)
Context: tasks 4.1–4.2. expo-file-system's `UploadTask` (native upload with progress) returns
the response body only as text, so a binary MP4 answer would be corrupted.
Decision: API addition (contract stays compatible): `POST /v1/video?result=link` answers
`{"id","url"}` and keeps ONLY the cleaned result (the upload is deleted at once) until a
one-time `GET /v1/video/{id}` (32-hex id, validated; folder deleted right after sending) or the
15-minute sweep; unknown id → `404 not_found`. Native: `UploadTask` (multipart, progress,
AbortSignal) → `DownloadTask` into the cache. Web: `XMLHttpRequest` (upload progress,
`responseType: blob`) on the classic direct response. Size (≤100 MB) and duration (≤60 s) are
checked on the device first when the picker/browser tells us (`features/video/limits.ts`).
Two-stage progress per the mockup; the cleaning stage has no server progress, so it shows an
unanimated partial amber bar and no fake percentage. Cancel aborts the request. Preview with
`expo-video` ~57.0.5 (new dependency); save via the shared `saveMedia` (write-only permission
for photo or video; `granularPermissions: ["photo","video"]`), share via `shareMedia`.
Every server code maps to DESIGN copy (`features/video/errors.ts`); new copy rows video.*,
err.clean_video_failed.
Verified on web (headless Chrome, local server): veo-1 dropped → upload → cleaning → "Watermark
removed" → Download gives `veo-1-clean.mp4` with C2PA kept and no logo. 29 pytest pass (link
mode, one-time download, bad ids). Android not run yet (owner test).

## D-019 — Remote masks (2026-10-02)
Context: task 5.2 — masks must be updatable without an app release.
Decision: `GET /v1/masks` now returns masks.json **plus the mask data** (`masks`: id → mask
JSON) for every template and video template. The app (`features/masks/mask-store.ts`) at start
loads the cached bundle (AsyncStorage key `saaf.masks`), then fetches the server
(4 s timeout) and switches only if `core/remote.ts parseMasksBundle` accepts it (types, ranges,
every referenced mask present, sizes and encoding valid via `loadTemplates`); otherwise it keeps
the cached or bundled masks. `cleanImage` reads `getMasks()`.
Verified (web e2e, same build): server serving a copy with threshold 0.98 → "No Gemini watermark
found"; server with the normal masks → "Watermark removed".
Consequences: a bad remote file can never break cleaning (falls back). Phase 6: the masks the
server serves become the "live" masks; edit them there (or point `SAAF_MASKS_DIR` elsewhere).

## D-020 — Android test APK: icon, permissions, local HTTP (2026-10-02)
Context: task 5.3.
Decision:
- Icon/splash generated from tokens by `apps/app/scripts/build-icons.cjs` (CanvasKit +
  Unbounded): a lowercase "s" in onNeem on Neem; adaptive icon layers, monochrome, splash
  marks (light + dark, on paper backgrounds), favicon. No third-party brand marks. Re-run after
  the owner picks the final name. Unused template images and `assets/expo.icon` deleted.
- Android package id `app.saaf.cleaner` (change before any store upload if the name changes).
- `blockedPermissions`: RECORD_AUDIO, SYSTEM_ALERT_WINDOW; expo-image-picker with camera and
  microphone off. Remaining: INTERNET, photo/video read (picker on old Android),
  WRITE_EXTERNAL_STORAGE ≤ API 32 (saving on old Android), VIBRATE.
- `expo-build-properties` ~57.0.22 with `android.usesCleartextTraffic: true` so a release APK
  can reach the local `http://<PC IP>:8000` server. **Turn it off in Phase 6** (HTTPS).
- Local build (no EAS account needed): `npx expo prebuild --platform android --clean`, then
  `android\gradlew assembleRelease` with `JAVA_HOME` = Android Studio's `jbr` and
  `EXPO_PUBLIC_API_URL=http://<PC Wi-Fi IP>:8000`. The release build uses the debug signing key
  (fine for testers, not for the Play Store). `android/` is generated and gitignored.
Addendum to D-017/D-018 (2026-10-02, Phase 3+4 review):
- Upload guard (ASGI middleware, runs before the body is read): rate-limit check, then
  `Content-Length > 101 MiB` → 413 at once; chunked bodies are counted and cut off. The rate
  limit now counts **successful cleans only** (matches "You've cleaned 10 videos this hour").
- Processing: `asyncio.Semaphore(2)` around worker-thread jobs (waiting jobs no longer hold
  threads); upload copy and folder deletes off the event loop; ffprobe 30 s / encode 600 s
  timeouts; decoder stopped first and every child reaped on any error (no Windows file lock
  keeping uploads); a decode with fewer frames than `nb_frames` or a non-zero ffmpeg exit is
  `processing_failed`, not a short 200; rotated phone videos use display width/height.
- Link mode: the job is claimed atomically (rename) so the download is truly one-time, served
  whole (Range ignored); `DELETE /v1/video/{id}` for cancels; link results expire after 5 min;
  the sweep runs every minute (15 min max for any job). Duration limit 60.5 s on both sides.
- App: native upload validates the job id, runs in a foreground session, releases tasks,
  deletes partial downloads, tells the server to DELETE on cancel, maps an HTTP 404 to
  `clean_video_failed`; web XHR always settles; stale runs cannot overwrite state; Share is

## D-021 — Responsive layout: one hook for phones, tablets and desktop (2026-10-02)
Context: owner asked that the one codebase look right on small phones, normal phones,
tablets and the web, not just a fixed 480 px column.
Decision: `ui/responsive-layout.ts` (pure, tested) + `useResponsive()` (`useWindowDimensions`,
updates on rotation and browser resize). Size classes, same on iOS/Android/web: compact
(< 360 wide or < 640 tall), phone, tablet (≥ 600), desktop (≥ 1024). From the class it derives
gutter (16/24/32/40), single-column width (480 → 560), split width (1040), title size
(22/28/32), Home pick-area height (32 % of the height, 180–340) and `mediaMaxHeight`.
`Screen` uses it; `splitOnWide` (Result, Video) puts media left and actions right on desktop
windows ≥ 560 tall. `CompareSlider` and the video preview are sized with `fitMedia` so tall
portrait images never push the actions off screen; on frames < 220 px wide the After/Before
tags move under the slider. Text honours the system font size up to 1.4×.
Verified with headless Chrome device emulation at 320×568, 390×844, 768×1024, 1440×900: no
horizontal overflow, the Download button stays on screen at every size.
